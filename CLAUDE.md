# Wheel

A native macOS and iOS agent development environment: a grid of panes (terminals, agent chats, web views) per project, one space per project, all state held by a Rust daemon.

## Layout

- `daemon/` — `wheeld`, the Rust daemon (PTYs, agents, spaces, permissions, artifacts). Its terminal emulator, `ghostty-vt`, builds libghostty-vt with Zig 0.16: `.cargo/config.toml` points cargo at `tools/zig`, which runs it through `mise` (installed on first use), so cargo needs `mise` on PATH and must run from inside the repo. `tools/zig` also points `zig build`'s cache at `~/.cache/wheel/ghostty-zig` (under `$XDG_CACHE_HOME` when set), shared by every checkout and target, so Ghostty compiles once per machine and version; `rm -rf ~/.cache/wheel/ghostty-zig` clears it, and the next build fills it again.
  A build from a fresh target needs the network twice: `ghostty-vt-sys`'s build script downloads Ghostty's source tarball, and `zig build` fetches Zig packages (`uucode`, `translate-c`) into `~/.cache/zig`. Offline works once both are local: extract the tarball named in `GHOSTTY.lock` (inside the `ghostty-vt-sys` crate in `~/.cargo/registry/src`) into a directory, export `GHOSTTY_SOURCE_DIR=<that directory>`, and build once online so `~/.cache/zig` fills. After that `cargo build --offline` succeeds with the network dead (checked: 51s from an empty target, proxies pointing at a closed port). An empty `~/.cache/zig` fails offline even with `GHOSTTY_SOURCE_DIR` set.
- An artifact opened in a space shows that space's project only, read from the space's directory (`WHEEL_SPACE_DIR` for its refresh command). One machine artifact serves every space by reading where it is opened; it has no control for viewing another space's data and no dropdown or setting for anything the space already says (ADR-0019).
- `artifacts/` — the built-in artifacts `wheeld` embeds (one folder each, `builtin.toml` holding its version) and installs from Settings › Artifacts or `wheel artifact builtin`.
- `cli/` — `wheel`, the CLI over the daemon's socket; the programmatic surface every check drives.
- `apple/` — SwiftUI clients: shared `WheelKit` package plus the Mac and iOS apps (Xcode project generated by xcodegen).
- `docs/adr/` — decisions. Read ADR-0001 and ADR-0002 before changing how clients, the daemon or the agents fit together, ADR-0003 and ADR-0011 before changing what a web pane shows, ADR-0012 before changing how a pane switches between terminal and chat, ADR-0004 before changing what defines an artifact, ADR-0010 before changing how a post reaches its renderer, ADR-0005 before changing what a browser pane may point at or where settings live, ADR-0013 before making Wheel run, or expect to find on the machine, anything its app bundle does not carry, ADR-0020 before deciding whether work goes in the client or the server, ADR-0014, ADR-0021 and ADR-0022 before changing how windows, sessions and spaces relate or what a client shows, ADR-0023 before naming anything about an agent, ADR-0024 before changing how a phone is notified, ADR-0017 before changing what the agent brief says, ADR-0025 before giving a machine artifact a command, script or default of its own, ADR-0029 before adding or changing a component a plugin's server lays out, and ADR-0030 before changing how streams merge or where they write, and ADR-0031 before adding or changing a component a page can name.
- `DESIGN.md` — layout and visual direction. Early slices use stock macOS styling.

## Components a page can name

A page names a component of the A2UI library (`a2ui-swift`, sources under `apple/WheelUI/.build/checkouts/a2ui-swift`) or a SwiftUI control under its SwiftUI name, and styles it with SwiftUI modifiers. Before adding a view to `apple/WheelUI/Sources/WheelUI/A2UI`, search the library and SwiftUI for it and use theirs. Wheel adds a component only when neither has one (today only `Canvas`), after an ADR names what was checked (ADR-0031). A wrapper around a control the library or SwiftUI already has, a restyled copy, or a page-shaped component is not added. Epic `wheel-cmbu.20` removes the wrappers that exist.

The `gallery` artifact shows every component, option and modifier the client draws. Any change to one (a property, a modifier, an addition, a deletion) updates the gallery in the same turn, and the report says what it now shows.

When the user asks for an ADR, write it to `docs/adr`, commit it and land it in the same turn, and say so in the report; its text in chat is the report, never a draft waiting for approval.

## Tracking

Work is tracked in beads (`bd`, prefix `wheel`). `bd ready` shows what is unblocked.

## Wheel Dev's daemon

Wheel Dev.app registers its own daemon (`com.piercemakes.wheel.dev.daemon`, port 7422) as a login item with `KeepAlive`, so it keeps running after the dev app quits, and killing the process only restarts it. When you are done testing with Wheel Dev, unload it with `launchctl bootout gui/$(id -u)/com.piercemakes.wheel.dev.daemon`; it comes back the next time Wheel Dev starts or you log in. A `UserPromptSubmit` hook (`.claude/hooks/dev-daemon-reminder.sh`) reminds you while it is loaded.

## Tasks

This project uses no `admin` tool, overriding the global rule that every project gets an `admin.toml`: the tracked `Makefile` holds every task (`make help` lists them), and Wheel's runner calls it. The runner buttons are `[runner]` entries in this machine's `~/.wheel/wheel.toml`, so every space's runner and command palette offer them: `wheel: deploy`, `wheel: restart server`, `wheel: dev deploy` and `wheel: dev restart server`, each `make -C <repo> <target>`. Anything else admin did is an artifact's job.

## The client and the server deploy separately

This is a hard rule (ADR-0020):

- Never deploy everything together. `make deploy-client` replaces the app and leaves the running `wheeld` alone; `make restart-server` is a separate step, taken only when a landed change needs it, because it ends every terminal and agent.
- Change the server only when the work needs what only the server holds: processes, files, other clients. Everything else goes in the client.
- Deploy the server only when a landed change touched `daemon/` or `proto/`.
- The server depends on nothing in the client and runs with no client attached.
- A server change a client relies on (a new op, or a field whose absence the client must notice) raises `PROTOCOL_VERSION` in `proto/src/lib.rs` and `ServerProtocol.current` in WheelKit together; against an older server the app hides what needs the new one and shows only "The server was updated." with Restart Server, and the `wheel` command refuses with "restart the server".

## Deploying Wheel from inside Wheel

`make deploy-client` (the runner's `deploy`) builds the Release app and installs it as `/Applications/Wheel.app` through `tools/install-app.sh`. The running app, its terminals and the agent that started the deploy stay up through the whole build; the script stops the app only for the two renames that swap the bundles, then relaunches it with a Finder-like environment. It stops only processes whose executable lies inside the bundle, so `wheeld` keeps running, and the relaunched app never restarts it: it compares the running `wheeld`'s source hash with the bundled one's and, when they differ, says so in the menu bar item and Settings › General and offers Restart Server. Confirm afterwards that the `wheeld` pid is unchanged and the app log says `same; nothing to offer` or `different; restart offered`. The script ignores the hangup the app's stop can send its pane and writes everything to `~/Library/Logs/wheel/deploy-release.log` (xcodebuild's own output to `deploy-release-xcodebuild.log`). Never `pkill` Wheel, never run a step that quits it before the new build is finished and staged, and confirm afterwards that `pgrep -x Wheel` shows a process started after the install.

The server is a bundle that does not run from inside the app. `apple/Mac/embed-wheeld.sh` builds `Contents/Helpers/Wheel Server.wheelserver` (`Wheel Dev Server.wheelserver` in the dev app; the extension is not `.app`) holding `Contents/MacOS/wheeld`, an `Info.plist` made from `daemon/Info.plist.in` (name, bundle id, `LSUIElement`, the folder usage strings) and `ServerIcon.icns` (`tools/render-server-icon.sh` renders it from `apple/Mac/ServerIcon/ServerIcon.svg`), and signs the executable and then the bundle. macOS charges folder access to a program that runs from inside Wheel.app to Wheel, whatever its own bundle id says, so the app copies the bundle out: `Contents/Resources/wheel-server.sh start`, which the app runs at launch, ditto-copies it to `~/Library/Application Support/Wheel/Server/Versions/<source hash>/Wheel Server.app` (`Wheel Dev` and `Wheel Dev Server.app` for the dev app) through a staging folder and an atomic rename, never touching a version that exists, and loads a plain launch agent, `~/Library/LaunchAgents/<label>.plist`, whose program is `Server/Current/Wheel Server.app/Contents/MacOS/wheeld` and whose arguments include `--cli <app>/Contents/Helpers/wheel`. `start` leaves a job that is running alone. `Current` moves, and the job restarts, only in `wheel-server.sh restart` (the app's Restart Server, `make restart-server`), so a client deploy copies the new version and never runs it (ADR-0020). macOS lists the copy in Privacy & Security as Wheel Server and keeps its Desktop, Documents, Downloads and network-volume grants; the Mac app holds no file permission, and file work it once did itself (creating a `wheel.toml` to edit) is a server request. Verify with the Unified Log: `log show --last 2m --predicate 'subsystem == "com.apple.TCC"' --style compact | grep AUTHREQ_SUBJECT` names `com.piercemakes.wheel.daemon`, not `com.piercemakes.wheel`, and `launchctl print gui/$(id -u)/com.piercemakes.wheel.daemon` has no `parent bundle identifier`.

`make restart-server` (the runner's `restart server`) restarts `wheeld` from the installed bundle with `launchctl kickstart -k`, detached, since it ends the pane that ran it; `~/Library/Logs/wheel/restart-server.log` records the old and new pid. `make deploy-dev` and `make restart-server-dev` do the same for `/Applications/Wheel Dev.app` and its daemon.
