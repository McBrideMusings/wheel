# verify-project — wheel

Verification drives the real binaries, never only unit tests. Every check names the command run and the output it printed.

## 1. Build and tests

```bash
( cd ~/Projects/wheel && cargo build )
( cd ~/Projects/wheel && cargo clippy --all-targets -- -D warnings )
( cd ~/Projects/wheel && cargo test )
```

All three must pass. Run cargo from inside the repo (or a worktree of it): `.cargo/config.toml` points `ghostty-vt-sys` at `tools/zig` (Zig 0.16 through `mise`), and cargo reads that file only from a directory inside the repo. From elsewhere the build fails with `ghostty-vt-sys needs Zig 0.16.x, found 0.15.2`. From the repo root, `admin build daemon`, `admin vet` and `admin test rust` run the same commands, and `admin build mac` and `admin test wheelkit` the Apple ones (`admin.toml`, uncommitted). `daemon/tests/reattach.rs` is the PTY replay contract. A build from a fresh target needs the network (Ghostty's source tarball, and Zig packages into `~/.cache/zig`); with the network down it fails with `ghostty-vt-sys could not obtain the Ghostty source tarball ... Connection refused`, which is `BLOCKED`, not a code failure. `GHOSTTY_SOURCE_DIR=<extracted tarball>` plus a filled `~/.cache/zig` makes `cargo build --offline` work (see `CLAUDE.md`).

## 2. The daemon at its socket

Start a throwaway daemon on its own port and log directory, so a running `wheeld` on 7420 is never touched:

```bash
~/Projects/wheel/target/debug/wheeld --listen 127.0.0.1:7499 --log-dir /private/tmp/claude/Projects-wheel/verify-logs --support-dir /private/tmp/claude/Projects-wheel/verify-inst
```

`--support-dir` moves the whole instance directory — the token, the saved layout and the `shared` artifact root — so nothing in a run touches the real `~/Library/Application Support/wheel`. (`--token-file` and `--state-file` still override either file on its own.) Without it the daemon loads and rewrites the real `spaces.json`, respawning a shell for every saved terminal pane, and serves the real machine-wide artifacts.

Drive it with a client over `ws://127.0.0.1:7499/ws?token=<contents of the token file>`, using the `wheel` CLI once it exists (`wheel --url ws://127.0.0.1:7499/ws status`), otherwise a small Node script using Node's built-in `WebSocket`. A terminal check must show all of these:

- `term_open` returns `term_opened` with a pid;
- after a disconnect, a new connection's `term_attach` returns `term_attached` with `replay_bytes > 0`, and the replayed output contains a marker the shell printed before the disconnect (print it as the result of arithmetic, for example `echo wheel-$((40+2))`, so the echoed input can't satisfy the check);
- the replay is the daemon's copy of the screen (ghostty-vt), written out as output. With `vim -u NONE -n note.txt` running, `wheel term read <id> --timeout 0.3` prints the shell's screen and history first (the marker it printed before vim, the `vim` command line), then `ESC[?1049h ESC[H ESC[0m`, then vim's modes, the file's lines, the `~` rows and the message line, with the cursor near the end. The daemon log has `attach draws the shell screen behind the alternate screen term=<id> primary_bytes=N alternate_bytes=M`. In the Mac app: start vim in a terminal pane, relaunch the app, then `wheel term send <term> ':q!' --enter`; the pane's `viewport_text` shows the shell's earlier output again (for example `shell-42` from `echo shell-$((6*7))`), not just a fresh prompt;
- a connection with a wrong token is refused, and the log says `refused: missing or wrong token`;
- `status` lists the terminal with `alive: true` and reports `log_path`;
- `wheel term close <id>` exits 0 and `status` no longer lists it; closing it again exits 6 (`no terminal <id>`);
- a `term open` terminal whose shell runs `exit 7` with nobody attached stays in `status` with `alive: false`; a later `wheel term read <id> --until x` exits 4 (it saw the exit), after which `status` no longer lists it and another read exits 6;
- a pane's terminal (§2b) is refused by `term close` (exit 6, `belongs to a pane`), stays in `status` with `alive: false` after its shell exits, and leaves `status` when the pane closes;
- raw frames with no `req` — `term_input`, `term_resize`, `term_attach`, `term_close` on `t-missing` — each get `{"ev":"error","term":"t-missing","message":"no terminal t-missing"}`; a non-terminal op (`space_close` on `s-missing`) gets an error with no `term`; `wheel term send t-missing hi` exits 6;
- with a `term open` terminal and a `wheel term read` attached, `kill -TERM` (and, on a fresh daemon, `kill -INT`) makes wheeld exit 0 within about 10 ms, the shell's pid is gone, and the log's last line is `wheeld stopping signal=SIGTERM` (or `SIGINT`), and the attached `term read` exits 7 with `lost the connection to the daemon`; with `--lead-cmd wheel-fake-agent` the agent child is gone too.

Then read the log at the reported `log_path` and confirm this run wrote `wheeld listening`, `ws connect`, `pty spawned` (with `owner=Client` or `owner=Pane`), `attach` (with `replay_bytes`), `term closed`, `exited terminal dropped`, `pty killed`, `terminal op failed term=t-missing` and `ws close`.

`/private/tmp/claude/Projects-wheel/vcs-check.sh`, `et2-check.sh`, `j8p-check.sh` and `j8p-lead.sh` run these (scratch, not committed).

Stop the daemon by its PID when done.

## 2b. Spaces and the split tree

Same throwaway daemon, plus `--state-file /private/tmp/claude/Projects-wheel/spaces.json --no-lead` (delete the file first). With `W="wheel --url ws://127.0.0.1:7499/ws --token-file <token>"`:

- `$W space new /tmp` prints `s1`; `$W space ls` shows one space, `name: tmp`, `active: s1`, and one empty pane whose id is the space's `focus`;
- `$W pane split <pane> right` prints the new pane id; `$W pane kind <new> terminal` exits 0; `$W pane ratio <split> 0.3` exits 0; `$W pane focus <first pane>` exits 0;
- `$W pane split <pane> diagonal` exits 2; `$W pane close p999` exits 6;
- kill the daemon by PID and start it again with the same `--state-file`: `$W space ls` shows the same space, pane and split ids, `ratio: 0.3`, the same `focus`, and the terminal pane with a **new** term id that `$W status` lists `alive: true` in the space's cwd; `$W term send <term> 'echo pane-$((6*7))' --enter` then `$W term read <term> --until pane-42` exits 0;
- closing the focused pane focuses the pane beside it: with A | (B / C) and C focused, `$W pane close <C>` leaves `focus: <B>`; with (A / B) | C, closing C leaves `focus: <B>` (the left side's bottom-right); the log line is `pane closed ... focus=<B>`;
- closing both panes leaves `spaces: []`, `active: null` (closing the last pane closes its space);
- a hand-written `--state-file` whose layout holds `{"node":"pane","id":"p9","kind":"hologram","depth":3}` (with `next_id` above every id): wheeld starts, `$W space ls` shows that object unchanged, it is still in the file after another change, `$W pane kind p9 terminal` and `$W pane close p9` exit 0, and the log has `unknown pane kind; kept as is ... kind=hologram`. Wait for the port before the first CLI call; a fresh build can take over a second to bind;
- a hand-written `--state-file` with an extra top-level key (`"future_key":{"a":[1,2]}` beside `next_id`) starts wheeld, logs `unknown saved key; kept as is key=future_key`, and after any change (`$W space new /tmp`) the file still holds that key unchanged;
- the log has `space created`, `pane split`, `pane kind`, `split ratio`, `focus`, `spaces restored ... respawned=1`, `pty killed`, `pane closed` and `pane closed; it was the last, so space closed`.

## 2c. Web panes

Same throwaway daemon. A web pane shows an **artifact**, named by a scope and a name, never by a path: the daemon owns the three roots and resolves the folder itself. For a space whose directory is `<cwd>`, and the instance directory `<inst>` (the one holding `--state-file` and the token):

```
repo    <cwd>/.wheel/artifacts/<name>/
local   <cwd>/.wheel/local/artifacts/<name>/
shared  <inst>/artifacts/<name>/
```

`wheel artifact new` makes a folder; make one by hand when the check needs a folder that is wrong in a particular way. Put `index.html` (linking a relative `style.css`) and a `.env` in `<cwd>/.wheel/artifacts/site`; with a space's pane `<p>` and `B=http://127.0.0.1:7499/artifacts/<p>`:

- `$W pane kind <p> web` exits 6 (`a web pane needs artifact`); `$W pane kind <p> terminal --artifact site` exits 6 (`artifact and scope are only for a web pane`); `$W pane kind <p> web --artifact site` exits 0 and `$W space ls` shows `"kind": "web", "scope": "repo", "name": "site"` for the pane and a `web_panes` row giving that pane's `scope`, `name` and resolved `dir` (`<cwd>/.wheel/artifacts/site`);
- the three roots each serve: with `<cwd>/.wheel/local/artifacts/site` also made, `$W pane kind <p> web --artifact site` resolves `local` (a bare name tries local, then repo, then shared, and the pane stores the scope that won); `--scope repo` and `--scope shared` serve their own roots, each confirmed by the `web_panes` row's `dir`;
- `curl -D - "$B/index.html?token=<token>"` gets `303`, `location: /artifacts/<p>/index.html` (no token) and `set-cookie: wheel_token=…; Path=/artifacts/<p>/; HttpOnly; SameSite=Strict`; `curl -L -c jar` the same URL ends at 200 with the page; with `-b jar`, `style.css` is 200 `text/css`;
- a bearer header gets 200; no token 401; `../` (`curl --path-as-is`) and `%2e%2e` 404; `.env` 404; `Origin: http://evil.example` 403, `Origin: http://127.0.0.1:7499` 200; `?token=` on a pane that is not a web pane 404;
- start `$W pane wait-reload <p>` in the background, then edit `index.html`: it prints `pane_reload <p> at <unix ms>`, under 1000 ms after the write (about 215 ms is normal); writing only `.env` sends nothing;
- kill the daemon by PID and start it with the same `--state-file`: the log has `watching web pane pane=<p>` before `spaces restored`, and a write still reaches `wait-reload`;
- `$W status` lists `watches: [{pane, role, scope, name, dir, watching, waiting}]`, **two rows per web pane** — `role: "artifact"` for the artifact's folder and `role: "data"` for the pane's own data directory, in that order (`watching: null` while a watch could not be set; wheeld retries every second and logs `retrying every second`). A hand-written `--state-file` whose web pane names an artifact with no folder: the pane restores **still showing that artifact** (`space ls` shows its `scope` and `name`, never `kind: empty`) and `watches` shows `waiting: true` with `watching` on the nearest existing folder above its `dir`; `mkdir` the folder and write `index.html` and a running `wait-reload` prints `pane_reload` under 1000 ms (about 220 ms), `watching` is now the folder with `waiting: false`; `rm -rf` it and `waiting` is `true` again within 0.6 s, `mkdir` it again and a write still reaches `wait-reload`; `$W pane kind <p> terminal` leaves `watches: []`. The log has `watching web pane … waiting=true`, `pane reload … appeared=true`;
- no scope-and-name input names a folder outside the three roots, so there is nothing to refuse by path: `$W pane kind <p> web --artifact` with `/`, `/etc`, `..`, `.`, `.env`, `a/b`, `../out` or `-x`, and with an empty name, exits non-zero — anything but one plain name is refused at parse (`is not an artifact name`), and a plain name no root has is refused as `no artifact <name>: nothing at <three paths>` rather than guessed at. `--dir` no longer exists: `$W pane kind <p> web --dir /etc` exits 2 (`unexpected argument`). MCP `set_pane_kind` with `artifact: "/etc"` or `artifact: ".."` returns `isError: true` with the parse text; without `artifact` it returns `isError: true` (`a web pane needs artifact`); with `artifact: "site"` it returns `<pane> is now web`. There is no `may_show` and no restore-to-empty rule left in the tree — `rg 'may_show|is outside space' daemon cli proto apple` prints nothing;
- the scope's root is the whole rule for a served file, and the artifact's folder is just the first name under it: replacing the artifact folder with a symlink to `/etc` makes `$B/hosts` 404, so a cloned repo cannot ship `.wheel/artifacts/<name>` as a link to the home directory and have the pane serve it; `../`, `%2e%2e`, `.env` and a symlink *inside* the folder pointing out are all 404 too, each logged as `artifact not found, or outside the pane's folder`;
- a pane this build cannot read never costs the layout: a hand-written `--state-file` whose web pane carries `"name": "../out"`, or `"scope": "hologram"`, or no `name` at all, still starts wheeld — `space ls` shows that pane object **unchanged**, the log has `unknown pane kind; kept as is … kind=web`, it is still in the file after another change, and the other spaces are all there;
- the log has `watching web pane`, `artifact token traded for a cookie`, `artifact served … bytes=`, `pane reload pane=<p> … changes=`, `refused: browser origin`, `refused: missing or wrong token via="artifacts …"` and `stopped watching web pane` when the pane closes or changes kind.

Each pane showing an artifact also gets a **data directory of its own** at `<inst>/panes/<p>/`, served under the reserved `data/` prefix of that pane's URL. It is keyed by the pane and never by the artifact, so one shared artifact open in two projects reads and writes two separate directories, and nothing generated lands in a project's working tree. The refresh command below is the only thing the daemon writes there; a file put in by hand checks the serving on its own.

- opening the pane makes the directory — `$W pane kind <p> web --artifact viewer --scope shared` and `<inst>/panes/<p>/` is there, while the artifact's own folder gains nothing and no `panes/` appears under `<cwd>`;
- write `rows.json` into it and `curl -b jar "$B/data/rows.json"` is 200 `application/json` with those bytes; a file in a subdirectory serves as `data/sub/x.txt`; the artifact's own files still serve from their own paths;
- the data root keeps every refusal the artifact's folder has, from the same resolver: `data/../../etc/passwd` (`curl --path-as-is`), `data//etc/passwd`, `data/.env`, a symlink inside it pointing out, another pane's directory through `data/../<other pane>/rows.json`, and a missing file are all 404; without the cookie or token it is 401;
- an artifact's own `data/` is unreachable, not merely shadowed: `mkdir <artifact>/data` and write a different `rows.json` in it, and `$B/data/rows.json` still serves the pane's bytes, while `artifact show` reports `data/ is reserved`;
- a write in the data directory reaches a running `$W pane wait-reload <p>` under 1000 ms, the same `pane_reload` a write in the artifact's folder sends;
- the directory goes when the pane does: `$W pane kind <p> empty` removes `<inst>/panes/<p>/` and leaves no `watches` row for that pane (the other pane keeps its two); showing an artifact again makes a fresh, empty directory; `$W pane close` and `$W space close` remove it the same way. The log has `removed the pane's data directory`, and every `watching web pane` and `pane reload` line carries `role=Artifact` or `role=Data`, so a log read afterwards says which of a pane's two directories changed;
- removal is off the spaces lock: with 90,000 files in a pane's data directory, `pane kind <p> empty` returns and a following `status` answers in tens of ms; `<inst>/panes/<p>` is gone at once (the tree is renamed to `panes/.gone-*` and deleted on a thread, log `removed the pane's data directory`), and a `.gone-*` left by a stop is deleted at the next start (`removed a pane data directory left from the last run`). `/private/tmp/claude/Projects-wheel/jci8-check.sh` runs it (scratch);
- a restore sweeps what no layout names: with `<inst>/panes/p7/sub/rows.json` beside a `--state-file` whose only web pane is `p1`, starting wheeld removes `panes/p7` (log `swept a pane data directory no layout names`) and leaves `panes/p1` and its files intact (`a_restore_sweeps_pane_data_directories_no_layout_names` in `daemon/tests/spaces.rs`);
- a restarted daemon with the same `--state-file` watches both roots again and makes the directory again, which the pane serves from — its contents do not survive the restart, since nothing yet writes them.

An artifact's definition is `artifact.toml` in its folder — `title`, an optional `command`, an optional `every` in seconds and an optional `pane` — and the folder is the whole of it: **nothing about an artifact is in the saved state file**, so `grep` the `--state-file` for an artifact's name and find only the panes that show it. Every artifact verb resolves `repo` and `local` against a space — the active one, or `--space <id>` — so with no space at all each exits 6 (`no space to resolve an artifact against`). The manifest's `command` is run for the pane showing the artifact once a person approves it (below), and `every` puts that run on a timer the pane owns.

- `$W artifact new dash` prints `<cwd>/.wheel/artifacts/dash` on stdout (the scope and title go to stderr), and the folder holds `artifact.toml` starting `title = "dash"`, an `index.html`, and no `data/`; `$W artifact new dash` again exits 6 (`there is already a repo artifact dash`), so nothing an artifact holds is overwritten; `--artifact`-style bad names (`a/b`, `..`, `.env`, empty, `/etc`, `-x`) each exit non-zero;
- `$W artifact new dash --scope local` prints `<cwd>/.wheel/local/artifacts/dash` and leaves `.wheel/local/` in `<cwd>/.gitignore` **exactly once** over two local creations (`grep -c '^\.wheel/local/$'` is 1); `--scope shared` prints `<inst>/artifacts/viewer`;
- one rule answers for reading, writing and listing: a root or a folder that leads out of the directory it belongs to is served by nothing, written to by nothing and listed by nothing. With `.wheel/artifacts` in a second project made a symlink to a folder elsewhere, `$W artifact new out --scope repo --space <s2>` exits 6 (`… leads out of …`) and that folder stays **empty** — the check runs before the first `mkdir`, so not even an empty directory appears there. With an artifact folder inside a real root made a symlink to a folder outside it, `artifact ls --json` does not list it and `artifact show <name> --scope repo` exits 6, so no manifest is read from outside its scope;
- a creation that fails leaves no folder to block the retry: with the `local` root `chmod 500`, `artifact new ro --scope local` exits non-zero, and after `chmod 700` the same name is made;
- every manifest problem is in the record wherever the artifact is listed or shown, never only in the log: a folder with no `artifact.toml` reports `no manifest`; one holding `colour = 1` and `every = 2` with no `index.html` and a `data/` directory reports `unknown key colour, which nothing reads`, `every asks for a refresh on a timer, but no command says what to run`, `no index.html` and `data/ is reserved …` — all four in `artifact show broken --json` and as `problem:` lines in plain `artifact show broken`, which still reports `every: 2`. `every = 0`, `-5`, `1.5` or `"soon"` each report `every is not a positive whole number of seconds`; `title = ""` or `command = "  "` report `title is empty` / `command is empty` and the value is not taken, so a blank command never satisfies `every`; a manifest that is not TOML reports `artifact.toml is not valid TOML: …`;
- a pane on that broken artifact still serves its static files: write `index.html` into it, `$W pane kind <p> web --artifact broken --scope repo`, and `curl -L -c jar "$B/index.html?token=<token>"` is 200 with the page while `artifact show` still lists the problems;
- `$W artifact ls --json` reports every artifact in all three scopes, each with `scope`, `name`, `dir`, `title`, `pane` and `problems`, ordered local, repo, shared — the order a bare name resolves in — plus `resolves`, naming the scope each bare name lands in (`dash -> local` with the name in two scopes); plain `artifact ls` prints the same records and a closing `a bare name resolves to:` list, and with nothing anywhere prints nothing on stdout and `[no artifacts in any scope]` on stderr;
- `pane = true` is what offers an artifact in a pane picker, and the two registries are the scopes: `shared` is every project on this machine, `repo` and `local` are the project's own. `$W artifact new dash --pane` writes the flag (and a plain `artifact new` writes `# pane = true` as a comment, so the key is visible to whoever opens the file); `artifact show` reports `pane: true|false` and plain `artifact show` adds `(in the pane picker)` to the flagged one's first line; `artifact ls --pane` lists only the flagged ones — for a space with its own flagged `repo` artifact and a flagged `shared` one, exactly those two, and another space's flagged `repo` artifact never appears in it. Unfiltered, the one-offs are listed too, still ordered local, repo, shared, and every record carries the flag. `artifact ls --pane` on a space with none exits 0 printing `[no artifact in any scope asks for the pane picker]` on stderr. `pane = "yes"` is reported as `pane is not true or false`, the artifact reports `pane: false`, `artifact show` still exits 0, and a pane can still show it — the flag decides what a *picker* offers, never what can be opened;
- `resolves` is unaffected by the filter: with an **unflagged** `repo` artifact and a **flagged** `shared` one of the same name, `artifact ls --pane` reports `resolves: {viewer: repo}` while listing only the shared one, so a picker is told that the bare name would open something else;
- `$W artifact show dash --json` is one such record for the scope a bare name wins; `--scope repo` takes that root instead; a name nowhere (`nosuch`) and a name that scope lacks (`viewer --scope repo`) each exit 6;
- the log has `artifact created`, `gitignored the local artifact root`, `artifact has problems … problems=4` and `artifact request refused`.

A manifest that declares a `command` makes the pane **refresh**: wheeld runs that command when the pane opens, whenever asked, and — when the manifest declares `every` — every that many seconds, in the space's directory, with `WHEEL_PANE`, `WHEEL_SPACE_DIR` and `WHEEL_DATA_DIR` in its environment — and only after a person approves it at a permission request. Approval is remembered in `<inst>/artifact-trust.json`, keyed by the artifact's **folder** and the command. `wheel artifact refresh <pane>` runs one on demand and exits 1 when the run failed; `wheel artifact trust [--json]` lists the remembered pairs and `--forget <name>` drops an artifact's. A refresh needs two processes: the one asking waits for its reply, so the answer comes from another (`wheel perm wait` then `wheel perm answer`), as it does from a client.

- opening the pane raises a request `$W perm wait` prints, whose `title` names the command, `repo artifact dash` and the space's directory, and whose `session` is the pane; `$W perm answer <id> allow` runs it, and what it wrote serves at `$B/data/rows.json` (200, the command's bytes) while the artifact's own folder gains no `data/` and the project's working tree gains nothing;
- the command runs in the **space's** directory (`pwd` written into the data directory is `<cwd>`) with `WHEEL_PANE=<p>`, `WHEEL_SPACE_DIR=<cwd>` and `WHEEL_DATA_DIR=<inst>/panes/<p>` (`env | grep ^WHEEL_` written there says so);
- `$W status` carries `refreshes: [{pane, scope, name, dir, cwd, data_dir, command, every, timer, runs, last}]`, one row per refreshing pane, `last` being `{started_ms, duration_ms, exit, error, stderr_tail}` — `started_ms` a real unix ms time, `exit: 0` and no `error` for the run above;
- `allow` is not remembered (`$W artifact trust --json` is `[]`) and the next run asks again; `always` runs it and remembers the pair — `artifact trust` lists the folder, the command and the `name` it was approved as, `<inst>/artifact-trust.json` is there, and `grep` the `--state-file` for the command finds nothing, so no approval is in the saved layout;
- a command that runs project code is never remembered: with `command = 'sh refresh.sh'` (also `python3 tools/gen.py`, `node build.js`, `cat <space dir>/x`), `$W perm wait` lists only `allow` and `deny` (no `always`), and an `always` answer sent anyway is refused; a hand-written `artifact-trust.json` row for it is not honoured, so the timer reports `untrusted`;
- a remembered pair runs with nothing waiting on a person (`$W perm list` is `[]`) — including after killing wheeld and starting it again on the same `--state-file`: the restored pane's opening run writes the data directory with no request, and the log has `refresh command already trusted`;
- `$W artifact trust --forget dash` leaves `[]` and the next `artifact refresh` asks again; `--forget nosuch` exits 6;
- editing `command` in the manifest raises a fresh request and runs what the manifest says now — with `command = 'printf "boom\n" >&2; exit 3'`, `$W artifact refresh <p>` exits 1 printing `exit 3`, `status` reports `exit: 3` and `stderr_tail: "boom\n"`, and `$B/index.html` is still 200: a failing refresh is not a blank pane;
- a refusal is the run's result, not an error that loses it: `$W perm answer <id> deny` and `artifact refresh` exits 1 with `the person refused this command`, `status` reports that as `last.error` with no `exit`, the command's file is not written, and the pane still serves 200;
- a refresh's own write reloads the page: `$W pane wait-reload <p>` in the background prints `pane_reload <p>` for the run's write, the same reload a person editing that directory sends. Nothing in this build lets a page ask for a refresh, so no page reloads itself;
- `every` runs it on a timer the pane owns, and the row's `timer` says what that timer would do **now** — read from the manifest, the trust file and the timer task itself whenever the row is made, never remembered from the last tick. Five values: `ticking`; `untrusted` (skipping, because the command is not remembered as approved); `idle` (skipping, because `artifact.toml` asks for no `every` or no `command`); `off` (this pane has no timer: its manifest asked for no `every` when the pane opened); `stopped` (the timer task is gone while the pane still shows the artifact — only a daemon fault does that). With `every = 1` and the command answered `always`: the run count climbs by at least 3 in 6 seconds with `perm list` staying `[]` — **a tick never raises a request** — `last.started_ms` advances, `timer` is `"ticking"`, and `artifact refresh <p>` prints `on open, on demand and every 1s`;
- a tick that cannot run skips and says why in the log, rather than asking or ending the timer. Editing `command` to one nobody has approved makes `timer` `"untrusted"` at once, the run count stop where the runs left it, the new command write nothing, and `perm list` stay `[]`; answering `always` to one on-demand `artifact refresh` resumes the timer with no pane reopened and the count climbs again. Dropping `every` from the manifest makes `timer` `"idle"` and the count stop; putting it back resumes the timer at the next tick;
- a pane that opened on a manifest with no `every` has no timer, and the row never pretends otherwise: adding `every = 1` to that manifest makes the row report `every: 1` with `timer: "off"`, the plain row print `every 1s starts when the pane next shows it`, and nothing tick in the next 2.5 seconds. A manifest with a `command` and no `every` at all reports `every: null`, `timer: "off"`, prints `on open and on demand`, and leaves the count at 1 three seconds after the open;

## 2c-browser. Browser panes

A pane can be an ordinary browser rather than an artifact: `PaneKind::Browser { url }`, which carries the page it is on and nothing of the daemon's. `$W pane kind <p> browser [--page <url>]` opens one — the flag is `--page`, not `--url`, because `--url` is the CLI's own flag for the daemon's address — and `$W pane page <p> <text>` moves it the way typing `<text>` into the pane's address field does (`pane_browser_open`), printing the page the daemon read it as. The client reports where the person went with `pane_browser_url`, which anything else sending also moves that pane.

- with no `--page` it opens the `browser.homepage` setting as it resolves **for that pane's space** (§2d): with wheel's default, `about:blank`; with a project's `wheel.toml` setting one, that page, while a pane in another space opens the machine-wide value. `space ls` reports `"kind": "browser"` with that `url`;
- `--page https://example.com/one` opens exactly that, and `pane page <p> "https://example.com/two?q=1#x"` moves it, which `space ls` then reports. Reporting the page it is already on is accepted and changes nothing;
- the daemon reads typed text, for every client and the CLI alike (`wheel_proto::page_typed`): `pane page <p> example.com` prints `https://example.com`, `localhost:3000/x` gets `https://` with its port, `/tmp/a b.html` prints `file:///tmp/a%20b.html`, `~/x.html` is under wheeld's `$HOME`, and a space after the host is sent as `%20`. Text with a scheme is taken as typed, so `mailto:a@b.com`, `ftp://example.com` and `file:/tmp/a.html` are exit 6 (`isn't a web address or a file path`) rather than read as a host. Typing the page the pane is already on still replies `opened`, so the asking client loads it again;
- one rule answers for what any pane may point at: `file://otherhost/etc/passwd`, `file:relative.html`, `data:text/html,<p>x`, `javascript:alert(1)`, a bare `https://` and `about:config` are each exit 6 on **every** path — opening, typed text and a client's report — and the pane stays on the page it was on. Opening and a report name `an http:// or https:// URL with a host, a file:/// URL, or about:blank`, and refuse `example.com`, which only typed text reads as a web address. A scheme is matched without case (`HTTPS://Example.com` opens), and a URL with no real host (`http://:80`, `https://@/`, `http://user@`) or whitespace in it (`https://a b/c`) is refused;
- the fields belong to their own kinds: `--page` on a terminal exits 6 (`url is only for a browser pane`), `--artifact` on a browser exits 6 (`artifact and scope are only for a web pane`), `pane page` on a terminal pane exits 6 (`is not a browser pane`), and on a pane that does not exist exits 6;
- none of the artifact machinery is reached: a browser pane has no `watches` row, no `refreshes` row and no `<inst>/panes/<p>/` directory, and `/artifacts/<p>/index.html?token=…` is 404 — the daemon serves a browser pane nothing;
- the rule holds against the **file** as well as against a caller: a hand-edited `--state-file` whose browser pane carries `javascript:alert(1)` restores as a pane this build cannot draw (`space ls` shows `kind: "browser"` kept whole as an unknown pane, never a browser pane on that page), and a browser pane with no `url` at all does the same rather than failing the whole layout. A field this build does not read (`"zoom": 1.5` beside the kind) survives navigation, which changes the page; changing the pane's *kind* drops it with everything else the old kind held;
- a pane that *was* showing an artifact gives everything up when it becomes a browser: its two `watches` rows and its `<inst>/panes/<p>/` directory are gone afterwards, which is the assertion that would pass trivially for a pane that had never been a web pane;
- a page changes as often as a person loads one, so a navigation tells clients **one field** and the file is written **once per burst**: `pane page` twenty times in a row leaves `space ls` reporting the twentieth at once, and a moment later the file holds `example.com/20` and no earlier page with **`status`'s `layout_saves` up by exactly 1** — the daemon counts its own writes, which is the only thing a program can compare to tell one write per burst from one write each; an mtime check races the window and fails on a loaded machine instead. Every connection gets a `pane_url` frame per navigation and **no `spaces` frame for one** (`browsing_tells_clients_one_field_and_writes_the_file_once_per_burst` asserts both). Any other change to the layout — a split, say — still writes the file at once, and `SIGTERM` writes a page navigated to in the last moment, so a restart comes back on it. The log has `browser pane navigated` per navigation; the save itself logs at debug, so how often it saved is read from the file's mtime;
- the page is layout, so it survives: kill wheeld by PID, start it on the same `--state-file`, and `space ls` shows the pane on the same `url` with nothing restarted for it. `$W pane kind <p> empty` leaves an empty pane. The log has `browser pane navigated` with `from` and `to`;
- a file on this machine is a page: `--page file:///tmp/notes/index.html` opens and `pane page <p> file:///…` moves the pane, on both paths;
- WheelKit decodes a browser pane and reports a `browser` pane with no `url` as a kind it cannot draw (`ProtocolTests.decodesABrowserPane`). The Mac app's browser pane is §4.

## 2d. Settings
