# Verify — wheel

Verification drives the real binaries, never only unit tests. Every check names the command run and the output it printed.

`tools/` beside this file holds one script per section (`daemon.sh` § 2, `spaces.sh` § 2b, `web.sh` § 2c, `browser.sh` § 2c-browser, `settings.sh` § 2d, `usage.sh` § 3f) and `all.sh`, which runs them in turn. Run `cargo build` first. Each script uses `target/debug` (or `$CARGO_TARGET_DIR/debug`), starts its own daemon on a free port (searched upward from a number derived from `$SWARM_WORKER` when it is set, else a random one) with a `mktemp` support directory, prints one `ok` / `FAIL` line per check and `N passed, M failed`, exits non-zero on a failure, and stops its daemon and removes its directory on exit. `lib.sh` holds the helpers. Host dependencies, all macOS: `plutil` (reads the JSON), `curl`, `perl` (millisecond timing), `pgrep`, BSD `sed`; The daemon runs terminals under `/bin/sh`, so a slow login shell cannot time a check out. The sections below still say what each check proves and list what no script covers.

## 1. Build and tests

```bash
( cd ~/Projects/wheel && cargo build )
( cd ~/Projects/wheel && cargo clippy --all-targets -- -D warnings )
( cd ~/Projects/wheel && cargo test )
```

All three must pass. Run cargo from inside the repo (or a worktree of it): `.cargo/config.toml` points `ghostty-vt-sys` at `tools/zig` (Zig 0.16 through `mise`), and cargo reads that file only from a directory inside the repo. From elsewhere the build fails with `ghostty-vt-sys needs Zig 0.16.x, found 0.15.2`. From the repo root, `admin build daemon`, `admin vet` and `admin test rust` run the same commands, and `admin build mac` and `admin test wheelkit` the Apple ones (`admin.toml`, uncommitted). `daemon/tests/reattach.rs` is the PTY replay contract. A build from a fresh target needs the network (Ghostty's source tarball, and Zig packages into `~/.cache/zig`); with the network down it fails with `ghostty-vt-sys could not obtain the Ghostty source tarball ... Connection refused`, which is `BLOCKED`, not a code failure. `GHOSTTY_SOURCE_DIR=<extracted tarball>` plus a filled `~/.cache/zig` makes `cargo build --offline` work (see `CLAUDE.md`).

## 2. The daemon at its socket

Start a throwaway daemon on its own port and log directory, so a running `wheeld` on 7420 is never touched:

```bash
~/Projects/wheel/target/debug/wheeld --listen 127.0.0.1:7499 --log-dir <logs> --support-dir <inst> --machine-file <inst>/wheel.toml
```

`<inst>` and `<logs>` are fresh directories of your own (`mktemp -d`). `--support-dir` moves the whole instance directory — the token, the saved layout and the `machine` artifacts' folders — and `--machine-file <inst>/wheel.toml` moves the machine `wheel.toml` (settings and `machine` artifact entries; `~/.wheel/wheel.toml` by default), so nothing in a run touches the real `~/Library/Application Support/wheel` or `~/.wheel`. (`--token-file` and `--state-file` still override either file on its own.) Without it the daemon loads and rewrites the real `spaces.json`, respawning a shell for every saved terminal pane, and serves the real machine-wide artifacts.

Drive it with a client over `ws://127.0.0.1:7499/ws?token=<contents of the token file>`, using the `wheel` CLI once it exists (`wheel --url ws://127.0.0.1:7499/ws status`), otherwise a small Node script using Node's built-in `WebSocket`. A terminal check must show all of these:

- `term_open` returns `term_opened` with a pid;
- after a disconnect, a new connection's `term_attach` returns `term_attached` with `replay_bytes > 0`, and the replayed output contains a marker the shell printed before the disconnect (print it as the result of arithmetic, for example `echo wheel-$((40+2))`, so the echoed input can't satisfy the check);
- the replay is the daemon's copy of the screen (ghostty-vt), written out as output. With `vim -u NONE -n note.txt` running, `wheel term read <id> --timeout 0.3` prints the shell's screen and history first (the marker it printed before vim, the `vim` command line), then `ESC[?1049h ESC[H ESC[0m`, then vim's modes, the file's lines, the `~` rows and the message line, with the cursor near the end. The daemon log has `attach draws the shell screen behind the alternate screen term=<id> primary_bytes=N alternate_bytes=M`. In the Mac app: start vim in a terminal pane, relaunch the app, then `wheel term send <term> ':q!' --enter`; the pane's `viewport_text` shows the shell's earlier output again (for example `shell-42` from `echo shell-$((6*7))`), not just a fresh prompt;
- a connection with a wrong token is refused, and the log says `refused: missing or wrong token`;
- `status` lists the terminal with `alive: true` and reports `log_path`;
- `wheel term close <id>` exits 0 and `status` no longer lists it; closing it again exits 6 (`no terminal <id>`);
- a `term open` terminal whose shell runs `exit 7` with nobody attached stays in `status` with `alive: false`; a later `wheel term read <id> --until x` exits 4 (it saw the exit), after which `status` no longer lists it and another read exits 6;
- a pane's terminal (§2b) is refused by `term close` (exit 6, `belongs to a pane`), stays in `status` with `alive: false` after its shell exits, and leaves `status` when the pane closes;
- raw frames with no `req` — `term_input`, `term_resize`, `term_attach`, `term_close` on `t-missing` — each get `{"ev":"error","term":"t-missing","message":"no terminal t-missing"}`; a non-terminal op (`space_close` on `s-missing`) gets an error with no `term`; `wheel term send t-missing hi` exits 6;
- with a `term open` terminal and a `wheel term read` attached, `kill -TERM` (and, on a fresh daemon, `kill -INT`) makes wheeld exit 0 within about 10 ms, the shell's pid is gone, and the log's last line is `wheeld stopping signal=SIGTERM` (or `SIGINT`), and the attached `term read` exits 7 with `lost the connection to the daemon`; with `agent.claude.command` set to `wheel-fake-agent` and an agent pane started, the agent child is gone too.

Then read the log at the reported `log_path` and confirm this run wrote `wheeld listening`, `pty spawned` (with `owner=Client` or `owner=Pane`), `attach` (with `replay_bytes`), `term closed`, `exited terminal dropped`, `pty killed`, `terminal op failed term=t-missing`. `ws connect` and `ws close` are debug lines for a local client (start the daemon with `WHEEL_LOG=debug` to see them) and info for a paired device; the Mac app logs `Mac app attached` at info.

`tools/daemon.sh` runs these (29 checks: terminals, replay across a reconnect, the refused token, exit codes 4, 6 and 7, SIGTERM and SIGINT each exit 0 within 1 s, where the spec above says about 10 ms: the script allows for a loaded machine, the fake agent child dying with the daemon, the log lines). It starts its own daemon on a free port and removes everything it made. Not scripted: raw frames with no `req`, and the vim alternate-screen replay.

Stop the daemon by its PID when done.

## 2b. Spaces and the split tree

Same throwaway daemon, plus `--state-file <state>` (a path of your own; delete the file first). With `W="wheel --url ws://127.0.0.1:7499/ws --token-file <token>"`:

- `$W space new /tmp` prints `s1`; `$W space ls` shows one space, `name: tmp`, `active: s1`, and one empty pane whose id is the space's `focus`;
- `$W space ls --json` prints a bare array `[{id, name, cwd, status, panes}]` (`panes` = pane ids, `status` null when no pane runs an agent); plain `space ls` still prints the `{spaces, active, web_panes}` layout. Committed test: `space_ls_json_is_a_flat_array_of_id_name_cwd_status_and_pane_ids`;
- `$W pane split <pane> right` prints the new pane id; `$W pane kind <new> terminal` exits 0; `$W pane ratio <split> 0.3` exits 0; `$W pane focus <first pane>` exits 0;
- `$W pane split <pane> diagonal` exits 2; `$W pane close p999` exits 6;
- kill the daemon by PID and start it again with the same `--state-file`: `$W space ls` shows the same space, pane and split ids, `ratio: 0.3`, the same `focus`, and the terminal pane with a **new** term id that `$W status` lists `alive: true` in the space's cwd; `$W term send <term> 'echo pane-$((6*7))' --enter` then `$W term read <term> --until pane-42` exits 0;
- closing the focused pane focuses the pane beside it: with A | (B / C) and C focused, `$W pane close <C>` leaves `focus: <B>`; with (A / B) | C, closing C leaves `focus: <B>` (the left side's bottom-right); the log line is `pane closed ... focus=<B>`;
- closing a space's last pane exits 0 and leaves the space, now holding one new `empty` pane (a new id) that is its `focus`, which survives a daemon restart; closing every pane keeps every space, and `$W space close <id>` per space leaves `spaces: []`, `active: null`;
- a hand-written `--state-file` whose layout holds `{"node":"pane","id":"p9","kind":"hologram","depth":3}` (with `next_id` above every id): wheeld starts, `$W space ls` shows that object unchanged, it is still in the file after another change, `$W pane kind p9 terminal` and `$W pane close p9` exit 0, and the log has `unknown pane kind; kept as is ... kind=hologram`. Wait for the port before the first CLI call; a fresh build can take over a second to bind;
- a hand-written `--state-file` with an extra top-level key (`"future_key":{"a":[1,2]}` beside `next_id`) starts wheeld, logs `unknown saved key; kept as is key=future_key`, and after any change (`$W space new /tmp`) the file still holds that key unchanged;
- the log has `space created`, `pane split`, `pane kind`, `split ratio`, `focus`, `spaces restored ... respawned=1`, `pty killed`, `pane closed` and `pane closed; it was the last, so the space holds one empty pane`.

Recent directories: every `space new` puts its directory at the top of `spaces.json`'s `recent` list (`[{dir, opened_ms}]`, one row per directory, newest first, at most 50), written beside the layout and restored with it; a restore records nothing. `$W space recent [--json]` prints it (`dir` is the path the CLI canonicalised, so `/tmp/a` reads `/private/tmp/a`). After `space new` on directories A, B, A and closing each, the list is A then B; it is the same after killing and restarting wheeld on the same `--state-file`. The log has `space recent recorded dir=… opened_ms=… rows=` and `space recent restored rows=`. Committed test: `recent_directories_list_newest_first_once_each_and_survive_a_restart`.

Browsing: `$W space browse <path> [--json]` lists the subfolders of a folder and marks one open as a space with `(space <id>)`; `/no/such/dir` exits 1 printing `no folder at /no/such/dir`; `$W config get spaces.roots` with nothing set prints `~` plus the parent of every recent space, and `$W space browse` with no path lists those roots. The log has `dir_list path=… count=`, `dir_list refused` and `dir_roots count=`. Committed tests: `dir_list_names_subfolders_marks_open_spaces_and_says_why_it_cannot`, `spaces_roots_default_to_home_and_the_parents_of_recent_spaces`.

`tools/spaces.sh` runs these (61 checks).

Terminal panes also save what they were doing (`resume.rs`). The daemon samples each terminal's foreground process every 2 s and when it stops, and saves `cwd` and, while Claude Code or Codex runs there, `agent: {name, session, home}` in the pane. A program for the check: copy `/bin/sleep` to `<bin>/claude` (`codesign -f -s -`), put `<bin>` on `PATH`, give wheeld `CLAUDE_CONFIG_DIR=<ch>`, run `$W term send <term> 'claude 3000' --enter`, then write `<ch>/projects/<space dir with every non-alphanumeric as ->/<uuid>.jsonl` while `sleep` still runs (only a transcript written at or after the agent process's start time can be its session, so a file made before `claude` starts is not picked; the daemon reads the start time with `proc_pidinfo` on macOS and `/proc` on Linux, and logs `cannot read when the agent's process started; not guessing its session` and saves no session when it cannot), wait 5 s, and the state file's pane holds `cwd` and `agent.session = <uuid>`. `kill -TERM` wheeld and start it again on the same `--state-file`: `$W term read <new term>` shows `claude --resume <uuid>` typed in a shell whose `status` cwd is the saved one, and the log has `pane restored ... kind="terminal" outcome=shell in <dir>; resumed claude session <uuid>`. A session the agent no longer has, a second pane naming a session already resumed, and a directory that has gone each get a plain shell, and the outcome says why. Every restored pane logs one `pane restored` line with its `kind` and `outcome`. Committed test: `a_terminal_restores_into_its_last_directory_and_resumes_its_agent`.

A terminal pane's `agent` also carries `context: {used, size}`, the agent's own figures. Claude Code: the `claude` wrapper adds `--settings` with a `statusLine` whose command is `wheel pane statusline`; it reads Claude Code's status-line input on stdin (`context_window.context_window_size`, and the sum of `context_window.current_usage`), sends it to the daemon (`pane_report_context`), then runs the person's own `statusLine` command (project `.claude/settings.local.json`, `.claude/settings.json`, then `$CLAUDE_CONFIG_DIR/settings.json`) on the same input and prints what it prints. pi: the extension `pi-status.ts` runs `wheel pane report-context --used N --size M` after every turn from `ctx.getContextUsage()`. Codex: the sampler reads the newest `token_count` event of the rollout: `last_token_usage.total_tokens` and `model_context_window`. The daemon logs `terminal agent reported its context` at debug (`WHEEL_LOG=debug`); a context-only change broadcasts the layout without writing it or logging `terminal pane saves its directory and agent`. `tools/terminal-context.sh` (by name, one prompt on the real Claude account) proves Claude: `$W space ls` shows `agent.context.size` equal to the window in the saved status-line input (1,000,000 on Opus 5.5), and the project's own status line still receives the input. Committed tests: `codex_context` in `resume.rs` (`a_codex_rollouts_last_token_count_is_the_context_use`), `cli/src/statusline.rs`, and the `pane_report_context` calls in `daemon/tests/spaces.rs`. The Mac app's debug `/state` shows that pane's `context.text` as a percentage, and `used / size` after `POST /context/toggle?pane=<p>`.

A terminal pane's Claude `agent.session` follows `/clear`, `/resume` and `/compact`, which keep the process: the wrapper's `SessionStart` hook runs `wheel pane report-session` (reads `session_id` from the hook input), the daemon logs `terminal agent reported its session`, and the next sample saves it, so `pane view <p>` reads `terminal <new id>` and a switch to the agent view and back keeps it. The daemon takes the report only when the reporter's nearest Claude Code ancestor is the terminal's foreground program; any other (`claude -p` started by a tool, a plain shell) is refused with `<p>'s foreground program did not send this report` and logged `session report ignored`. `tools/terminal-session.sh` proves it with a node stand-in named `claude` (needs `$CARGO_TARGET_DIR`): an outsider report exits 6, then after the stand-in's hook the view reads `terminal 66666666-…`.

## 2c. Web panes

Same throwaway daemon. A web pane shows an **artifact**, named by a scope and a name, never by a path. An artifact is one `[artifacts.<name>]` entry in a `wheel.toml` (ADR-0004), and the entry's `path` names the page — a folder, whose page is `index.html`, or one HTML file — anywhere on the machine, relative to the file holding the entry. For a space whose directory is `<cwd>`, and the instance directory `<inst>` (the one holding `--state-file` and the token):

```
project  <cwd>/wheel.toml   [artifacts.<name>] path = "…"
machine  <inst>/wheel.toml  [artifacts.<name>] path = "…"
```

`wheel artifact new` makes a folder and its entry; write the entry by hand when the check needs one that is wrong in a particular way. Put `index.html` (linking a relative `style.css`) and a `.env` in `<cwd>/site`, and `[artifacts.site]` with `path = "site"` in `<cwd>/wheel.toml`; with a space's pane `<p>` and `B=http://127.0.0.1:7499/artifacts/<p>`:

- `$W pane kind <p> web` exits 6 (`a web pane needs artifact`); `$W pane kind <p> terminal --artifact site` exits 6 (`artifact and scope are only for a web pane`); `$W pane kind <p> web --artifact site` exits 0 and `$W space ls` shows `"kind": "web", "scope": "project", "name": "site"` for the pane and a `web_panes` row giving that pane's `scope`, `name` and watched `dir` (`<cwd>/site`, links followed);
- both registries serve: with a `site` entry also in `<inst>/wheel.toml`, `$W pane kind <p> web --artifact site` still resolves `project` (a bare name tries project, then machine, and the pane stores the scope that won); `--scope machine` serves the machine entry's folder, confirmed by the `web_panes` row's `dir`;
- `curl -b jar "$B/"` (the folder's own address, which a client opens) is 200 with the page;
- `curl -D - "$B/index.html?token=<token>"` gets `303`, `location: /artifacts/<p>/index.html` (no token) and `set-cookie: wheel_token=…; Path=/artifacts/<p>/; HttpOnly; SameSite=Strict`; `curl -L -c jar` the same URL ends at 200 with the page; with `-b jar`, `style.css` is 200 `text/css`;
- a bearer header gets 200; no token 401; `../` (`curl --path-as-is`) and `%2e%2e` 404; `.env` 404; `Origin: http://evil.example` 403, `Origin: http://127.0.0.1:7499` 200; `?token=` on a pane that is not a web pane 404;
- start `$W pane wait-reload <p>` in the background, then edit `index.html`: it prints `pane_reload <p> at <unix ms>`, under 1000 ms after the write (about 215 ms is normal); writing only `.env` sends nothing;
- kill the daemon by PID and start it with the same `--state-file`: the log has `watching web pane pane=<p>` before `spaces restored`, and a write still reaches `wait-reload`;
- `$W status` lists `watches: [{pane, role, scope, name, dir, watching, waiting}]`, **two rows per web pane** — `role: "artifact"` for the artifact's folder and `role: "data"` for the pane's own data directory, in that order (`watching: null` while a watch could not be set; wheeld retries every second and logs `retrying every second`). A hand-written `--state-file` whose web pane names an artifact whose entry names a folder that is not there: the pane restores **still showing that artifact** (`space ls` shows its `scope` and `name`, never `kind: empty`) and `watches` shows `waiting: true` with `watching` on the nearest existing folder above its `dir`; `mkdir` the folder and write `index.html` and a running `wait-reload` prints `pane_reload` under 1000 ms (about 220 ms), `watching` is now the folder with `waiting: false`; `rm -rf` it and `waiting` is `true` again within 0.6 s, `mkdir` it again and a write still reaches `wait-reload`; `$W pane kind <p> terminal` leaves `watches: []`. The log has `watching web pane … waiting=true`, `pane reload … appeared=true`;
- repointing an open web pane's entry moves its artifact watch: with the pane showing `site` registered at `<A>`, rewrite its `path` in `wheel.toml` to `<B>` (an existing folder) and within 1 s `$W status` shows that pane's `role: "artifact"` row with `dir` and `watching` both `<B>`, a running `wait-reload` prints `pane_reload`, a write in `<A>` sends none, and a write in `<B>` sends one. The log has `artifact repointed; moving the watch from=<A> to=<B>` then `watching web pane … dir=<B>` and `pane reload … path=<B>`. `repointing_an_artifacts_entry_moves_the_open_panes_watch` in `daemon/tests/spaces.rs` covers it;
- a pane names an entry, never a folder, so there is nothing to refuse by path: `$W pane kind <p> web --artifact` with `/`, `/etc`, `..`, `.`, `.env`, `a/b`, `../out` or `-x`, and with an empty name, exits non-zero — anything but one plain name is refused at parse (`is not an artifact name`), and a plain name neither `wheel.toml` has is refused as `no artifact <name>: no entry for it in <cwd>/wheel.toml or <inst>/wheel.toml` rather than guessed at. `--dir` no longer exists: `$W pane kind <p> web --dir /etc` exits 2 (`unexpected argument`). There is no `may_show` and no restore-to-empty rule left in the tree — `rg 'may_show|is outside space' daemon cli proto apple` prints nothing;
- the page's real folder is the whole rule for a served file (ADR-0003): an entry may name a folder anywhere — `path = "../learn/course"` or `"/Users/…/course/sheet.html"` — and the pane serves `index.html` (or the named file) at `$B/`, `lessons/one.html` beside it, and nothing else: `../`, `%2e%2e`, `.git/config`, `.env` and a symlink *inside* the folder pointing out are all 404, each logged as `artifact not found, or outside the pane's folder`; an entry whose page is not there is 404 with `artifact not found: its page is not anywhere`. Committed test: `an_entry_serves_a_page_from_anywhere_and_nothing_outside_its_folder` in `daemon/tests/spaces.rs`;
- a pane this build cannot read never costs the layout: a hand-written `--state-file` whose web pane carries `"name": "../out"`, or `"scope": "hologram"`, or no `name` at all, still starts wheeld — `space ls` shows that pane object **unchanged**, the log has `unknown pane kind; kept as is … kind=web`, it is still in the file after another change, and the other spaces are all there;
- the log has `watching web pane`, `artifact token traded for a cookie`, `pane reload pane=<p> … changes=`, `refused: browser origin`, `refused: missing or wrong token via="artifacts …"` and `stopped watching web pane` when the pane closes or changes kind.

Each pane showing an artifact also gets a **data directory of its own** at `<inst>/panes/<p>/`, served under the reserved `data/` prefix of that pane's URL. It is keyed by the pane and never by the artifact, so one machine artifact open in two projects reads and writes two separate directories, and nothing generated lands in a project's working tree. The refresh command below is the only thing the daemon writes there; a file put in by hand checks the serving on its own.

- opening the pane makes the directory — `$W pane kind <p> web --artifact viewer --scope machine` and `<inst>/panes/<p>/` is there, while the artifact's own folder gains nothing and no `panes/` appears under `<cwd>`;
- write `rows.json` into it and `curl -b jar "$B/data/rows.json"` is 200 `application/json` with those bytes; a file in a subdirectory serves as `data/sub/x.txt`; the artifact's own files still serve from their own paths;
- the data root keeps every refusal the artifact's folder has, from the same resolver: `data/../../etc/passwd` (`curl --path-as-is`), `data//etc/passwd`, `data/.env`, a symlink inside it pointing out, another pane's directory through `data/../<other pane>/rows.json`, and a missing file are all 404; without the cookie or token it is 401;
- an artifact's own `data/` is unreachable, not merely shadowed: `mkdir <artifact folder>/data` and write a different `rows.json` in it, and `$B/data/rows.json` still serves the pane's bytes, while `artifact show` reports `data/ is reserved`;
- a write in the data directory reaches a running `$W pane wait-reload <p>` under 1000 ms, the same `pane_reload` a write in the artifact's folder sends;
- the directory goes when the pane does: `$W pane kind <p> empty` removes `<inst>/panes/<p>/` and leaves no `watches` row for that pane (the other pane keeps its two); showing an artifact again makes a fresh, empty directory; `$W pane close` and `$W space close` remove it the same way. The log has `removed the pane's data directory`, and every `watching web pane` and `pane reload` line carries `role=Artifact` or `role=Data`, so a log read afterwards says which of a pane's two directories changed;
- removal is off the spaces lock: with 90,000 files in a pane's data directory, `pane kind <p> empty` returns and a following `status` answers in tens of ms; `<inst>/panes/<p>` is gone at once (the tree is renamed to `panes/.gone-*` and deleted on a thread, log `removed the pane's data directory`), and a `.gone-*` left by a stop is deleted at the next start (`removed a pane data directory left from the last run`).;
- a restore sweeps what no layout names: with `<inst>/panes/p7/sub/rows.json` beside a `--state-file` whose only web pane is `p1`, starting wheeld removes `panes/p7` (log `swept a pane data directory no layout names`) and leaves `panes/p1` and its files intact (`a_restore_sweeps_pane_data_directories_no_layout_names` in `daemon/tests/spaces.rs`);
- a restarted daemon with the same `--state-file` watches both roots again and makes the directory again, which the pane serves from — its contents do not survive the restart, since nothing yet writes them.

An artifact's definition is its entry — `path`, `title`, an optional `command`, an optional `every` in seconds and an optional `pane` — and **nothing about an artifact is in the saved state file**, so `grep` the `--state-file` for an artifact's name and find only the panes that show it. Every artifact verb resolves `project` against a space — the active one, or `--space <id>` — so with no space at all each exits 6 (`no space to resolve an artifact against`). The entry's `command` is run for the pane showing the artifact (below), and `every` puts that run on a timer the pane owns.

- `$W artifact new dash` prints `<cwd>/.wheel/artifacts/dash` on stdout (the scope and title go to stderr); the folder holds only `index.html`, and `<cwd>/wheel.toml` gains `[artifacts.dash]` with `path = ".wheel/artifacts/dash"`, `title = "dash"` and `pane = false`. `$W artifact new dash` again exits 6 (`there is already a project artifact dash in <cwd>/wheel.toml`), so nothing an artifact holds is overwritten; bad names (`a/b`, `..`, `.env`, empty, `/etc`, `-x`) each exit non-zero;
- `--path <dir>` makes the folder anywhere (relative to the caller's directory) and the entry names it absolutely; `--scope machine` prints `<inst>/artifacts/<name>` and writes `<inst>/wheel.toml`; `--scope local` and `--scope repo` exit 2 (`is not one of the accepted values`), and nothing writes a `.gitignore`;
- the default folder still refuses a symlinked `.wheel`: with `.wheel/artifacts` in a second project made a symlink to a folder elsewhere, `$W artifact new out --space <s2>` exits 6 (`… leads out of …, so nothing is written there; give the folder with --path`) and that folder stays **empty**;
- a creation that fails leaves no folder to block the retry;
- every entry problem is in the record wherever the artifact is listed or shown, never only in the log: an entry with no `path` reports `no path, so there is no page to show`; one holding `colour = 1` and `every = 2`, naming a folder with no `index.html` and a `data/` directory, reports `unknown key colour, which nothing reads`, `every asks for a refresh on a timer, but no command says what to run`, `no index.html in <folder>` and `data/ is reserved …` — all four in `artifact show broken --json` and as `problem:` lines in plain `artifact show broken`, which still reports `every: 2`. `every = 0`, `-5`, `1.5` or `"soon"` each report `every is not a positive whole number of seconds`; `title = ""`, `command = "  "` or `path = ""` report `… is empty` and the value is not taken; a path with nothing there reports `nothing at <path>: …`. A `wheel.toml` that is not TOML makes `artifact ls` exit 6 naming that file, rather than listing the other registry without it;
- a pane on that broken artifact still serves its static files: write `index.html` into it, `$W pane kind <p> web --artifact broken`, and `curl -L -c jar "$B/?token=<token>"` is 200 with the page while `artifact show` still lists the problems;
- `$W artifact ls --json` reports every artifact of both registries, each with `scope`, `name`, `entry` (the `wheel.toml` holding it), `dir` (the page's real folder), `page`, `title`, `pane` and `problems`, ordered project then machine and by name within each — the order a bare name resolves in — plus `resolves`, naming the scope each bare name lands in; plain `artifact ls` prints each record's page path and `entry in <file>` and a closing `a bare name resolves to:` list, and with nothing anywhere prints nothing on stdout and `[no artifacts in any scope]` on stderr;
- `pane = true` is what offers an artifact in a pane picker, and the two registries are the scopes: `machine` is every project on this machine, `project` is the project's own. `$W artifact new dash --pane` writes `pane = true` (and a plain `artifact new` writes `pane = false`, so the key is visible to whoever opens the file); `artifact show` reports `pane: true|false` and plain `artifact show` adds `(in the pane picker)` to the flagged one's first line; `artifact ls --pane` lists only the flagged ones — for a space with its own flagged `project` artifact and a flagged `machine` one, exactly those two, and another space's flagged `project` artifact never appears in it. `pane = "yes"` is reported as `pane is not true or false`, the artifact reports `pane: false`, and a pane can still show it;
- `resolves` is unaffected by the filter: with an **unflagged** `project` artifact and a **flagged** `machine` one of the same name, `artifact ls --pane` reports `resolves: {viewer: project}` while listing only the machine one;
- `$W artifact show dash --json` is one such record for the scope a bare name wins; `--scope machine` takes that registry instead; a name nowhere (`nosuch`) and a name that scope lacks (`viewer --scope project`) each exit 6;
- `$W artifact add <path>` registers a page that already exists, from any directory (relative paths are this directory's): `artifact add ~/Learn/rainforest-interview-prep --pane` writes `[artifacts.rainforest-interview-prep]` with the absolute `path` into the space's `wheel.toml` (a folder inside the project is written relative), prints the record, and changes nothing in the folder (`git status` there is unchanged). A file registers under its name without the extension (`interview-sheet.html` → `interview-sheet`, `page: "interview-sheet.html"`; an `index.html` takes its folder's name); `--name`, `--title`, `--command`, `--every`, `--pane` and `--scope machine` set the rest. Each refusal exits 6 and leaves both files byte-identical: the same name again (`already`), a non-HTML file (`is not an HTML file`), a folder with no `index.html`, a path that is not there (`nothing at`), `--every` without `--command`, `--every 0`, an empty `--title` or `--command` — the entry reader's own problems, since add reads back what it would write before writing it. A link keeps its own name (`add ./link` is named `link`; the daemon follows it to locate the page). `$W artifact remove <name>` deletes the entry, prints the folder it named on stdout and `[removed project artifact <name> from <file>; its folder is left as it was]` on stderr; the folder is still there, a second remove exits 6, and a `[artifacts]` table the removal empties goes while other keys in the file stay. Committed test: `an_existing_page_is_registered_and_removed_without_touching_it`.;
- the log has `artifact created` (with `entry`), `artifact added`, `artifact removed`, `artifact has problems … problems=4` and `artifact request refused`.

An entry that declares a `command` makes the pane **refresh**: wheeld runs that command when the pane opens, whenever asked, and — when the entry declares `every` — every that many seconds, in the space's directory, with `WHEEL_PANE`, `WHEEL_SPACE_DIR` and `WHEEL_DATA_DIR` in its environment. It never raises a permission request and keeps no approval state. `wheel artifact refresh <pane>` runs one on demand and exits 1 when the run failed.

- opening the pane runs the command with `$W perm list` staying `[]`; what it wrote serves at `$B/data/rows.json` (200, the command's bytes) while the artifact's own folder gains no `data/` and the project's working tree gains nothing;
- the command runs in the **space's** directory (`pwd` written into the data directory is `<cwd>`) with `WHEEL_PANE=<p>`, `WHEEL_SPACE_DIR=<cwd>` and `WHEEL_DATA_DIR=<inst>/panes/<p>` (`env | grep ^WHEEL_` written there says so);
- `$W status` carries `refreshes: [{pane, scope, name, dir, cwd, data_dir, command, every, timer, runs, last}]`, one row per refreshing pane, `last` being `{started_ms, duration_ms, exit, error, stderr_tail}` — `started_ms` a real unix ms time, `exit: 0` and no `error` for the run above;
- editing `command` in the entry changes what runs — with `command = 'printf "boom\n" >&2; exit 3'`, `$W artifact refresh <p>` exits 1 printing `exit 3`, `status` reports `exit: 3` and `stderr_tail: "boom\n"`, and `$B/index.html` is still 200: a failing refresh is not a blank pane;
- a refresh's own write reloads the page: `$W pane wait-reload <p>` in the background prints `pane_reload <p>` for the run's write, the same reload a person editing that directory sends. Nothing in this build lets a page ask for a refresh, so no page reloads itself;
- `every` runs it on a timer the pane owns, and the row's `timer` says what that timer would do **now** — read from the entry and the timer task itself whenever the row is made, never remembered from the last tick. Four values: `ticking`; `idle` (skipping, because the entry asks for no `every` or no `command`, or its page is not there); `off` (this pane has no timer: its entry asked for no `every` when the pane opened); `stopped` (the timer task is gone while the pane still shows the artifact — only a daemon fault does that). With `every = 1`: the run count climbs by at least 3 in 6 seconds with `perm list` staying `[]`, `last.started_ms` advances, `timer` is `"ticking"`, and `artifact refresh <p>` prints `on open, on demand and every 1s`;
- a tick that cannot run skips and says why in the log, rather than ending the timer. Dropping `every` from the entry makes `timer` `"idle"` and the count stop; putting it back resumes the timer at the next tick;
- a pane that opened on an entry with no `every` has no timer, and the row never pretends otherwise: adding `every = 1` to that entry makes the row report `every: 1` with `timer: "off"`, the plain row print `every 1s starts when the pane next shows it`, and nothing tick in the next 2.5 seconds. An entry with a `command` and no `every` at all reports `every: null`, `timer: "off"`, prints `on open and on demand`, and leaves the count at 1 three seconds after the open;
- a run that outlasts its own interval is not overlapped by the next tick: with a command marking its own start and end in one file and `sleep 1.5` between them at `every = 1`, that file never holds two starts in a row (`[][][` — a trailing mark is a run in flight), and 6 seconds hold 2 runs rather than a queue of them. Editing `every` is picked up at the next tick: `1` to `5` makes the row report `5` and the count climb at most once in 3 seconds;
- the timer starts again when the daemon does: kill wheeld by PID and start it with the same `--state-file`, and the restored pane's row reports `timer: "ticking"` with its own count climbing past 3 in 6 seconds, `perm list` `[]` throughout. `$W pane kind <p> terminal` leaves `refreshes: []` and nothing in the data directory changes three seconds later;
- a run ends when its shell does, and nothing it started outlives it: the shell leads its own process group, killed when the shell exits, at the 60s limit and when the pane stops showing the artifact mid-run. `command = '(sleep 4711; touch "$WHEEL_DATA_DIR/late") & echo ran > "$WHEEL_DATA_DIR/rows"'` reports `exit: 0` with `duration_ms` in the tens, not 60000, though the backgrounded child held stderr, and `pgrep -f 'sleep 4711'` is empty with `refresh process group killed` in the log; a child that left the group and still holds stderr (`perl -MPOSIX -e 'POSIX::setsid(); exec "sleep", "4716"' & sleep 0.5; echo escaped >&2`) holds the run about 1s past its shell, not 60s, and `stderr_tail` keeps `escaped\n`; `'(sleep 4712; :) & sleep 4713; :'` refreshed on demand and then `pane kind <p> terminal` leaves no `sleep 4712` or `sleep 4713`; `'(sleep 4714; touch …/late) & sleep 4715; :'` reports `the command ran longer than 60s and was stopped` and leaves neither sleep alive nor `late` written. The trailing `; :` stops `/bin/sh` from exec'ing its last command, which would hide a shell-only kill;
- the group dies with wheeld, however wheeld dies: each run's group is led by a **warden** — `wheeld --refresh-warden`, started before the shell, which joins its group; the warden asks kqueue to wake it when wheeld exits (`NOTE_EXIT`) and holds no descriptor of wheeld's, so no other child can keep it from seeing the exit. With `'(sleep 4721; touch …/late) & sleep 4722; :'` running, `pgrep -f 'wheeld --refresh-warden'` finds exactly one, whose pid is the `sleep 4721`'s pgid and whose parent is wheeld; `kill -KILL` on wheeld leaves no `sleep 4721` or `sleep 4722` about 50 ms later, with no restart, no warden left and no `late` written; a restart on the same state file reruns the command, and `kill -TERM` on wheeld leaves nothing of it either. A run that finishes leaves no warden. The log has `refresh warden program` at start and `refresh warden armed` (with `pgid`) per run; a warden that never prints `armed` fails the run with `the refresh warden … did not say it was watching wheeld`;
- nothing to run is nothing to report: an artifact whose entry drops `command` leaves `refreshes: []` and `artifact refresh <p>` exits 6 (`declares no command`), a pane showing no artifact exits 6, and `$W pane kind <p> terminal` leaves `refreshes: []` with `stopped refreshing web pane` in the log;
- in the Mac app (§4) a request waiting for a web pane draws a card above the page (heading "This page wants to refresh its data", the request's title with the command and, after an edit, the changed file, and its options as buttons); the iOS web pane draws the same. Raise one with a project artifact whose `command` is `sh scripts/pull.sh`, `pane kind <p> web --artifact <name>`, and read `perms` / `waiting_count` from the debug `/state`; `POST /perm?id=<id>&choice=allow|always|deny` answers through the card's own path, and `wheel perm answer` from another client takes the card away (`waiting_count` 1 to 0). `wheel pane shot <p>` of such a pane is the window's drawing of the pane, so the card is in it;
- the log has `refreshing web pane`, `refresh timer armed` (with `every_secs`), `refresh end` at info only when the run failed (with `exit`, `error`, `duration_ms`, `stderr_bytes`), `refresh timer skipped a tick` (with why), `refresh process group killed` (with `pgid` and `left`, only when the run left something besides the warden to kill) and `stopped refreshing web pane`; `refresh start`, `refresh command finished`, `refresh warden armed`, `refresh process group had nothing left to kill`, `refresh end` of a successful run, `artifact served` and `page event stream opened` are debug lines (`WHEEL_LOG=debug`); `tool call`, `tool update` and `page data pushed` are too.

`tools/web.sh` runs §2c (159 checks): resolution across both registries, serving and the cookie trade, the refusals, reload, the pane data directory and its sweep, the artifact verbs (`new`, `add`, `remove`, `show`, `ls`, broken entries), a refresh and a failing one, and the page channel (a page PUT to `.wheel/state/<key>`, `artifact state [--wait]`, `artifact data` reaching `.wheel/events`). Not scripted: the 90,000-file removal timing, the refresh timer's four states and overlap rules, and the process-group and warden kill checks.

## 2c-browser. Browser panes

A pane can be an ordinary browser rather than an artifact: `PaneKind::Browser { url }`, which carries the page it is on and nothing of the daemon's. `$W pane kind <p> browser [--page <url>]` opens one — the flag is `--page`, not `--url`, because `--url` is the CLI's own flag for the daemon's address — and `$W pane page <p> <text>` moves it the way typing `<text>` into the pane's address field does (`pane_browser_open`), printing the page the daemon read it as. The client reports where the person went with `pane_browser_url`, which anything else sending also moves that pane.

- with no `--page` it opens the `browser.homepage` setting as it resolves **for that pane's space** (§2d): with wheel's default, `about:blank`; with a project's `wheel.toml` setting one, that page, while a pane in another space opens the machine-wide value. `space ls` reports `"kind": "browser"` with that `url`;
- `--page https://example.com/one` opens exactly that, and `pane page <p> "https://example.com/two?q=1#x"` moves it, which `space ls` then reports. Reporting the page it is already on is accepted and changes nothing;
- the daemon reads typed text, for every client and the CLI alike (`wheel_proto::page_typed`): `pane page <p> example.com` prints `https://example.com`, `localhost:3000/x` gets `https://` with its port, `/tmp/a b.html` prints `file:///tmp/a%20b.html`, `~/x.html` is under wheeld's `$HOME`, and a space after the host is sent as `%20`. Text with a scheme is taken as typed, so `mailto:a@b.com`, `ftp://example.com` and `file:/tmp/a.html` are exit 6 (`isn't a web address or a file path`) rather than read as a host. Typing the page the pane is already on still replies `opened`, so the asking client loads it again;
- one rule answers for what any pane may point at: `file://otherhost/etc/passwd`, `file:relative.html`, `data:text/html,<p>x`, `javascript:alert(1)`, a bare `https://` and `about:config` are each exit 6 on **every** path — opening, typed text and a client's report — and the pane stays on the page it was on. Opening and a report name `an http:// or https:// URL with a host, a file:/// URL, or about:blank`, and refuse `example.com`, which only typed text reads as a web address. A scheme is matched without case (`HTTPS://Example.com` opens), and a URL with no real host (`http://:80`, `https://@/`, `http://user@`) or whitespace in it (`https://a b/c`) is refused;
- the fields belong to their own kinds: `--page` on a terminal exits 6 (`url is only for a browser pane`), `--artifact` on a browser exits 6 (`artifact and scope are only for a web pane`), `pane page` on a terminal pane exits 6 (`is not a browser pane`), and on a pane that does not exist exits 6;
- none of the artifact machinery is reached: a browser pane has no `watches` row, no `refreshes` row and no `<inst>/panes/<p>/` directory, and `/artifacts/<p>/index.html?token=…` is 404 — the daemon serves a browser pane nothing;
- the rule holds against the **file** as well as against a caller: a hand-edited `--state-file` whose browser pane carries `javascript:alert(1)` restores as a pane this build cannot draw (`space ls` shows `kind: "browser"` kept whole as an unknown pane, never a browser pane on that page), and a browser pane with no `url` at all does the same rather than failing the whole layout. A field this build does not read (`"zoom": 1.5` beside the kind) survives navigation, which changes the page; changing the pane's *kind* drops it with everything else the old kind held;
- a pane that *was* showing an artifact gives everything up when it becomes a browser: its two `watches` rows and its `<inst>/panes/<p>/` directory are gone afterwards, which is the assertion that would pass trivially for a pane that had never been a web pane;
- a page changes as often as a person loads one, so a navigation tells clients **one field** and the file is written **once per burst**: `pane page` twenty times in a row leaves `space ls` reporting the twentieth at once, and a moment later the file holds `example.com/20` and no earlier page with **`status`'s `layout_saves` up by exactly 1** — the daemon counts its own writes, which is the only thing a program can compare to tell one write per burst from one write each; an mtime check races the window and fails on a loaded machine instead. Every connection gets a `pane_url` frame per navigation and **no `spaces` frame for one** (`browsing_tells_clients_one_field_and_writes_the_file_once_per_burst` asserts both). Any other change to the layout — a split, say — still writes the file at once, and `SIGTERM` writes a page navigated to in the last moment, so a restart comes back on it. The log has `browser pane navigated` per navigation; the save itself logs at debug, so how often it saved is read from the file's mtime;
- the page is layout, so it survives: kill wheeld by PID, start it on the same `--state-file`, and `space ls` shows the pane on the same `url` with nothing restarted for it. `$W pane kind <p> empty` leaves an empty pane. The log has `browser pane navigated` with `from` and `to`;
- a file on this machine is a page: `--page file:///tmp/notes/index.html` opens and `pane page <p> file:///…` moves the pane, on both paths;
- WheelKit decodes a browser pane and reports a `browser` pane with no `url` as a kind it cannot draw (`ProtocolTests.decodesABrowserPane`). The Mac app's browser pane is §4.

`tools/browser.sh` runs this (67 checks). A burst of twenty `pane page` calls is fired in parallel and the check allows at most 2 saves for it, because a loaded machine can spread the burst over more than one 400 ms window; `browsing_tells_clients_one_field_and_writes_the_file_once_per_burst` asserts exactly one.

## 2d. Settings

Wheel's own settings live in two `wheel.toml` files — one at the root of a space's directory, one in `<inst>` beside the token and the saved layout — and a key set in the project's file wins over the machine's, key by key, with a built-in default behind both. The daemon reads both files on every read, so a value changed by hand is in force at once. `wheel config ls [--space <id>] [--json]` reports every key with its value, its `origin` (`project` | `machine` | `default`), its `default`, one line of help, and each layer's own accepted value as `machine` and `project` (absent when that file sets nothing), so a project value still shows the machine value it hides; `wheel config get <key>` prints the bare value for a script; `wheel config set <key> <value> [--space <id>] [--machine]` writes one; `wheel config unset <key> [--space <id>] [--machine]` removes one from that file, so the layer below is in force. `wheel config homes <claude|codex|pi> [--path <p>] [--json]` lists the folders that agent could use as its home (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `PI_CODING_AGENT_DIR`; the default first, then folders under `$HOME` by name), one `<state>  <path>` line each, with `state` one of `valid` (holds the agent's data), `empty` (a new login), `missing` or `not_folder`; `--path` adds a `checked:` line for that one path (an empty `--path` asks about the default); an unknown agent exits with the daemon's refusal. ## Remote listener (wheel-1w1.1)

## 8. Log shipping and the usage journal (wheel-5c6d.1)

`cargo test -p wheeld --test logship` drives a fake Loki: a request is journaled with its labels and outcome (a failed one with its error), an app's `log` lines arrive as `source="app"`, nothing is sent twice, a closed port holds every line until the store answers, and with no `logs.push_url` the journal is still kept on disk and `status` says `off`.

Against the real store: start a wheeld with its own `--support-dir` and `--log-dir` on a free port, `wheel config set logs.push_url <url> --machine`, make a space, wait 8 s, and `logcli query --since=2m '{app="wheel", source="journal", host="<this Mac>"}'` returns the `space_create` line; `wheel status` shows `logs.state` `ok`. With the URL at a closed port, `logs.state` is `failing` with the connection error and `waiting_bytes` grows; setting the real URL delivers the held lines once. The daemon's log for the same window comes back under `source="wheeld"`.

**The apps' own lines (wheel-5c6d.2).** Both apps write their log through WheelKit's `AppLog`, and `DaemonClient` sends its lines to wheeld as `log` requests while connected, one batch in flight; wheeld's `ok` moves the saved position (`<log>.sent`: inode and byte offset, written to a temp file, synced, renamed). Lines written while wheeld is down wait in the file and go out on the next connection; a connection that drops after wheeld took a batch but before its `ok` arrived sends that batch again. Each file rolls to `<log>.1` past 10 MB. Every URL in a line is written without its user, password, query and fragment (`AppLog.write`), since the lines leave the device. The debug builds' `WHEEL_LOG_MARKS=<n>:<tag>` writes n numbered lines carrying the tag at launch. `swift test --package-path apple/WheelKit --filter AppLogTests` covers the reconnect, the roll and the redaction. Against the real store, with `LOKI_ADDR` and `LOKI_PUSH_URL` from `~/.claude/.env` exported: `mac-logship.sh` (needs `admin build mac`) and `ios-logship.sh` (needs `WHEEL_IOS_APP`, a pool simulator) each pair the app with their own daemon, stop the daemon, relaunch the app with five marks, start the daemon, and find each mark in `logcli query '{app="wheel", source="app", client="mac"|"iphone"}'` exactly once.

**Settings › General › Logs (wheel-5c6d.3).** The General tab draws `logs.push_url` as a field like any key (`config ls` reports it; the daemon reads it from this machine's file only) and, under it in the same box, the shipping state from `status` `logs`: off (grey, no URL), waiting (orange, no push to this URL yet), ok (green, `Arriving: last accepted <time>.`) or failing (red, `Failing: <error>`), with the bytes waiting on this Mac below. wheeld reports the state only in `status`, so the app asks for one every 5 s while the Settings window is open and takes only `logs` from those replies. `/state` `settings.logs` carries `url`, `state`, `last_ok_ms`, `waiting_bytes`, `error` and the row's `title` and `detail`; the app log has `log shipping: <state> to <url>, <n> bytes waiting[, error: …]` on each change of state, error or URL. ## 9. Keys (wheel-e19f)

The Mac app's keys follow Ghostty's defaults, with a Ghostty tab as a space and a split as a pane: ⌘N window, ⌘T New Space, ⌘D and ⇧⌘D split, ⌘W pane, ⌥⌘W space, ⇧⌘W window, ⌘[ ⌘] and ⌥⌘arrows move the focus, ⌃⌘arrows move a divider 5%, ⌃⌘= equalizes, ⇧⌘↩ zooms, ⇧⌘[ ⇧⌘] and ⌘1–⌘9 pick a space. Every action is one `CommandActions` entry with a built-in key; the `keybind` setting (machine only, Ghostty's spelling, comma separated: `cmd+k=split-right`, `cmd+d=unbind`, `clear`) applies over them, wheeld stores it in one spelling (`daemon/src/keybind.rs`) and WheelKit's `Keymap` applies it. A key monitor runs a bound key in a Wheel window before the menus or a terminal see it; the menus show the keys, and run them in other windows. A focused empty pane holds the keyboard: T terminal, 1–9 the found agents in button order, A artifact palette, B browser. A close or a kind change that ends a shell or an agent asks in an alert, where Return is yes and Esc is no. Settings › Keys draws the field and every action with its key, `set` beside one the setting changed, and the setting's problems.

`tools/hotkeys.sh` (needs `admin build mac`, 54 checks) presses every key with `POST /key?keys=` and reads `/state` `spaces`, `active`, `zoomed`, `first_responder`, `confirmation`, `keymap`, `keymap_problems` and `menus`: ⌘D from an empty pane and ⇧⌘D with a terminal holding the keyboard both split and hand the keyboard to the new empty pane; T and 1 start a terminal and the fake agent; the focus, divider, zoom and space keys; ⌘W asks, Esc in the alert keeps the pane, Return closes it; a palette kind change asks only over a running pane; `config set keybind` moves Split Right to ⌘K, frees ⌘D, and an unknown action shows in `keymap_problems`; with ⌘D unbound and a terminal holding the keyboard, ⌘D is taken by nothing (libghostty's default keybinds are cleared in `AppModel.controller`), while ⌘C and ⌘V are still taken by the surface; ⇧⌘W sends the spaces to the background. The app log has `key <chord>: <action>` per bound key and `keymap problem:` per unapplied entry. `cargo test -p wheeld --lib keybind` and `swift test --package-path apple/WheelKit --filter KeymapTests` cover the spelling both sides share.

`/key` offers the event in the order a key window does (keymap monitor, the views with a terminal first, the first responder) because AppKit gives a background app no keys; it leaves the main menu out, since `NSMenu` matches a key event made in code without its modifier flags. So the menus' own key equivalents (used outside Wheel windows, such as ⌘W closing Settings) are **not run by any check**: ⌘W in the Settings window closing it is checked by hand, with the app in front. Window shots of the empty pane's key hints, the Keys tab and the alert in light and dark are taken with `/window/snapshot` (`which=settings`, `which=sheet`).

`tools/shortcut-sheet.sh` (needs `admin build mac`, 25 checks) presses ⌘/ and Esc with `POST /key?keys=` and reads `/state` `shortcuts` (`open`, and `groups[].rows[]` with `id`, `title`, `keys`): the sheet opens and closes on ⌘/ and on Esc, lists the keys of Split Right/Down, Close Pane, Next/Previous Pane, Pane Left/Down, Next/Previous Space, Space 1 and 8, Zoom Pane and the Command Palette, and shows empty keys for Split Down once `keybind` unbinds it. The app log has `shortcut sheet: opened` and `shortcut sheet: closed`.
