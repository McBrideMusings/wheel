# ADR-0042: A pane script embeds a terminal, a web view or an agent chat by naming it

A pane script places another pane's terminal with `ui.Terminal{pane, height?}`, an agent pane's conversation with `ui.AgentChat{pane, height?}`, and a web page with `ui.WebView{url, height?}`. Each fills the width it is given and is `height` points tall (320 when the script gives none). `WebView` shows only `http` and `https` addresses; anything else draws a note in its place.

These are Wheel components under ADR-0031. Checked first: the A2UI library (`a2ui-swift`) has no terminal, agent conversation or web component; SwiftUI has no terminal or agent conversation, and its `WebView` (WebKit for SwiftUI) needs macOS 26 and iOS 26, above WheelUI's macOS 15 and iOS 18. `WebView` keeps that SwiftUI name and its `url` argument, so a page written for it reads the same when WheelUI moves to SwiftUI's.

`Terminal` and `AgentChat` name a pane by its id; they never start a process. A script finds ids in the `wheel.panes` and `wheel.agents` feeds. The pane keeps running and keeps its place in the grid; the embed is one more view of it, as a second client is. A terminal is sized to the newest view that asks, so the pane's grid view reflows while the embed is the newest.

WheelUI draws `WebView` itself with a `WKWebView`. It draws `Terminal` and `AgentChat` through the `a2uiPaneEmbed` environment closure the hosting client supplies, because the terminal and conversation views and their connections to `wheeld` belong to each client: the GPUI Mac client's bridge hosts its own Ghostty terminal views, and the iOS app its own terminal and transcript models. The closure answers every pane of a kind the client can show, with its own message for a pane that is gone, and answers nothing for a kind it cannot show, which WheelUI states in place. A client learns which terminal or agent a pane holds from its own layout: the GPUI client's Rust side sends the bridge a `pane_targets` map on every layout change, so `wheeld` gains no op.
