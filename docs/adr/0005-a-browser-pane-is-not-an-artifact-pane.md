# ADR-0005: A browser pane is not an artifact pane

A pane that shows a web page is one of two kinds. A `web` pane names an artifact by scope and name, has no browser chrome, and is served from its artifact's folder behind the daemon's token, as ADR-0003 sets out. A `browser` pane holds a page and draws an address field around it. Nothing about an artifact's folder applies to it — no folder, no data directory, no token, no cookie — so a page from the open internet never reaches the daemon's server; an artifact entry with a `url` only names the page it opens at.

A browser pane may point at an `http` or `https` URL with a host, a `file` URL naming an absolute path, or `about:blank`. A web pane points at one plain artifact name, never a path; showing an entry that carries a `url` makes the pane a browser pane at that page. A file page loads with read access to the whole disk, so its assets open and its scripts can read any file the user can. A file page names a path on the daemon's machine, and a client on another machine draws that pane as a file it cannot reach rather than loading a path of its own.

The rule for a page is `page_allowed` in `wheel_proto`, and wheeld applies it wherever a page arrives: a caller's request, a `wheel.toml` value, a pane in the saved layout, and the text a person types into an address field. Only wheeld reads that text, with `page_typed`, whose result passes the same rule. A client keeps only its web view's scheme policy.

A client that draws a browser pane's page itself, such as a phone, reaches a page on the Mac's loopback (`http://localhost:<port>`, `127.0.0.1`, `[::1]`) through wheeld: `/loopback/<port>/<path>` on its listener, with its token in a header, answers with `/<path>` from that port, and a redirect to the program's own address stays under `/loopback/<port>`. wheeld forwards only to a port some browser pane is on, so a paired device reaches the pages the person opened and no other service on the Mac's loopback, and it logs each forwarded request with the device, port, method and status.

The phone loads such a page under the `wheel-loopback` scheme, so the page's origin there is `wheel-loopback://localhost:<port>`. A loopback page may request any loopback port wheeld forwards. A page that is not under that scheme (a public site, or one framed in a loopback page) reaches no loopback port, and the phone cancels a non-GET navigation from one to the loopback. A request that carries no `Origin` (an image, a script, a frame) may only `GET` or `HEAD` another port than the page's, since it may come from another site framed in the page. A request to a port other than the page's is held to CORS as the Mac's browser holds it, with the page's Mac origin (`http://localhost:<port>`): the phone sends that origin in `Wheel-Page-Origin`, and wheeld refuses a value that is not a loopback origin, an origin on a port no browser pane's home is on, and a second copy, and passes the rest to the program as `Origin`. The phone sends the host the page named (`localhost`, `127.0.0.1`) in `Wheel-Page-Host`, and the program sees it with the port as `Host`, as the Mac's browser sends it. WebKit hands the phone's scheme handler a cross-origin request with the page's `Origin`, asks for its cookies only when the page asked for credentials, and checks `Access-Control-Allow-Origin` and `-Credentials` on the answer; the phone rewrites an `Access-Control-Allow-Origin` naming the page's Mac origin to the page's own before that check. WebKit sends no preflight for a custom scheme, so the phone sends the `OPTIONS` itself for a request that is not simple, and sends the request only when the answer allows its origin, method and headers (`LoopbackCORS` in WheelKit). Headers WebKit adds itself to revalidate an answer it holds (an `If-None-Match` or `If-Modified-Since` repeating that answer's validators, with `Cache-Control: max-age=0`) are not the page's and need no preflight. Each redirect of a cross-origin request passes the same `Access-Control-Allow-Origin` check before it is followed, and a request that needed a preflight is preflighted again where the redirect points, as the Fetch standard's redirect fetch does. A loopback cookie goes as its `SameSite` says, with the site the Mac's scheme and host (every port of `localhost` is one site, `127.0.0.1` another): `Strict` only same-site, `Lax` also on another site's top-level `GET` navigation, and one naming no `SameSite` as `None`, as WebKit sends it; a navigation the browser starts itself (an address, an agent's `open`, back, reload) is same-site. A page that names the other port as `http://localhost:<port>` leaves the scheme: its request goes to the phone's own loopback, never through wheeld.

*Page* is the term for what a browser pane points at. `url` names only the protocol fields that carry one.

Each client draws a browser pane's page in its own browser, and the pane's `url` is the page the pane opens at (ADR-0048). wheeld is never told where a browser goes, and sends no page to a client but the pane's `url` in the layout.

Settings live in two `wheel.toml` files, the same two that hold artifact entries (ADR-0004): a project's at the root of its space's directory, over this machine's at `~/.wheel/wheel.toml`, over a built-in default. A daemon started for a test or a swarm worker is given its own machine file, so it never reads or writes the real one. They resolve key by key. The saved layout holds no settings. Every value is checked when it is set and again when it is read from a file. A value that a layer sets and wheel refuses is reported as a problem on that key, and the layer below stays in force.
